# รีวิวพื้นที่ว่าง ความกว้าง และความหนาแน่นของหน้า — 10 ต.ค. 2569

สถานะ: **รีวิวและเสนอการแก้ ยังไม่ได้แก้ source code หรือ deploy**

## ขอบเขตและหลักฐาน

- ตรวจรายการ route จาก `src/app/**/page.tsx` ทั้ง 33 ไฟล์ รวม alias, auth, onboarding, print และ prototype
- เปิด Chrome จริงบน localhost ด้วยบัญชีทดสอบบทบาทผู้ขาย: 30 หน้า/มุมมอง × 5 ขนาดจอ = **150 กรณี**
- ขนาดจอ: 1440×1000, 1151×900, 768×1024, 390×844, 360×800
- ตรวจหน้าพิมพ์รายวันและรายสัปดาห์เพิ่มเติมที่ 1440px อีก 2 กรณี รวม **152 กรณีไม่ซ้ำ**
- เก็บ DOM snapshot, ภาพเต็มหน้า และค่าความกว้างจริง ดู [ตารางหลักฐาน](index.html), [measurements.json](measurements.json)
- รอ loading state หายและหัวข้อหน้าปรากฏก่อนเก็บผล ภาพ loading ในรอบสำรวจแรกถูกแทนด้วยเนื้อหาที่โหลดครบ
- ไม่พบ document horizontal overflow ใน 152 กรณีนี้ แต่พบการบีบข้อความ การยืดการ์ด และ scroll ซ้อน จึง **ไม่ถือว่า layout ผ่านเพียงเพราะไม่ล้นแนวนอน**
- ไม่เปลี่ยนข้อมูลผู้ใช้ บทบาท การตั้งค่า หรือสถานะงาน คืน viewport override แล้ว

## ประเด็นที่ควรแก้ ตามลำดับ

### 1. P1 — ปฏิทินเดือนบีบรายการนัดหมายและบิลจนสูง 0px

ในวันที่ 10 ต.ค. มีนัดหมายและบิลอยู่ใน DOM แต่กรอบรายการภายใน selected-day pane ถูก flex shrink จน `clientHeight=0` ขณะที่ `scrollHeight=134` ผู้ใช้จึงไม่เห็นข้อมูลที่มีอยู่จริงตามปกติ

- จุดตรวจ: `src/app/(app)/calendar/page.tsx:309` และ `CalendarContextItems` บรรทัด 336
- หลักฐาน: [calendar-scroll-details.json](calendar-scroll-details.json)
- แนวแก้: ไม่ให้ส่วนข้อมูลสำคัญถูกบีบความสูง; ลด scroll ซ้อน และวาง timeline กับรายการประกอบโดยมีขอบเขตความสูงชัดเจน
- เกณฑ์ผ่าน: นัดหมายและบิลที่มีข้อมูลต้องปรากฏจริงและเข้าถึงได้ทั้งเมาส์ สัมผัส และคีย์บอร์ด

### 2. P1 — TimelineBoard ใช้ breakpoint ของหน้าจอแทนพื้นที่ที่ได้รับ

หน้าเดือนแบ่งพื้นที่สองฝั่งเท่ากันตั้งแต่ 761px จากนั้น TimelineBoard ภายในฝั่งขวาแบ่งสองคอลัมน์อีกครั้งเมื่อ viewport ถึง `lg` โดยไม่คำนึงว่าตัวเองอยู่ในครึ่งหน้า

- ที่ 1440px: month card กว้าง 554px แต่ชื่อ task ในฝั่งขวาเหลือ **69px**; ชื่อทดสอบยาวสูงประมาณ **333px**
- ที่ 1151px: คำแนะนำฝั่ง timeline เหลือพื้นที่ประมาณ **57px**
- ปฏิทินวันและสัปดาห์ก็ได้รับผลที่ 1151px: ชื่อ task เหลือประมาณ **91px**
- ที่ 768px และมือถือ 360px: การ์ดเดือนยังเหลือพื้นที่ชื่อประมาณ **111px** เพราะ drag handle และปุ่มจัดเวลาอยู่ในแถวเดียวกัน
- จุดตรวจ: `calendar/page.tsx:289`, `TimelineBoard.tsx:950`, `TimelineBoard.tsx:1036`
- หลักฐาน: [เดือน 1440px](_calendar_view_month_date_2026_10_10_scope_all-1440.png), [เดือน 1151px](_calendar_view_month_date_2026_10_10_scope_all-1151.png), [วัน 1151px](_calendar_view_day_date_2026_10_10_scope_all-1151.png)
- แนวแก้: ใช้ความกว้าง container ตัดสินการแบ่งคอลัมน์; เดือนควรเป็นภาพรวมขนาดพอดีกับช่องวันที่ และให้รายละเอียดใช้พื้นที่ที่เหลือ; เมื่อพื้นที่ไม่พอให้ซ้อนแนวตั้ง ย้าย action ลงแถวถัดไปก่อนบีบชื่อ
- เกณฑ์ผ่าน: ข้อความชื่อไม่กลายเป็นคอลัมน์คำสั้น ๆ; drag handle และปุ่มยังใช้งานได้; วัน/สัปดาห์/เดือนใช้ข้อมูลและเวลาเดิม

### 3. P2 — เดือนมี scroll หลายชั้นและพื้นที่เลื่อนว่างท้ายหน้า

กรอบรายละเอียดจำกัดสูง 640px ภายในยังมีรายการงานและ timeline ที่เลื่อนแยกกัน ทำให้การเข้าถึงส่วนล่างไม่ชัดเจน โดยเฉพาะมือถือ

- ที่ 360px: body สูงประมาณ 1567px แต่ document scroll height ประมาณ 2355px ต่างกัน **788px**
- ที่ 1440px: body สูง 1000px แต่ document scroll height 1396px
- ยืนยันอาการจาก DOM และภาพแล้ว; ยังต้องไล่องค์ประกอบที่สร้าง overflow แนวตั้งก่อนสรุปสาเหตุระดับ CSS แบบเจาะจง
- หลักฐาน: [เดือน 360px](_calendar_view_month_date_2026_10_10_scope_all-360.png), [calendar-scroll-details.json](calendar-scroll-details.json)
- แนวแก้: มือถือให้หน้าเป็นตัวเลื่อนหลัก จำกัดการเลื่อนเฉพาะ timeline ที่จำเป็น และป้องกันลูกที่ถูก clip สร้างพื้นที่เลื่อนภายนอก

### 4. P2 — หน้าแผนปี/เดือน/สัปดาห์มีช่องว่างจากกลุ่มเป้าหมายสูงไม่เท่ากัน

`PlanGoalOverview` แสดงแต่ละด้านชีวิตเป็นการ์ดหนึ่งใบ โดยแสดงเป้าหมายทั้งหมดในใบนั้น แล้ววางใน grid ที่ยืดการ์ดตามแถว

- ที่ 1440px กลุ่มแรกสูง 517px และกลุ่มพัฒนาตัวเอง 4 เป้าหมายสูง 922px อยู่ในแถวใหม่เพียงกลุ่มเดียว ทำให้พื้นที่สองคอลัมน์ข้าง ๆ ว่าง
- ส่วนภาพรวมสูงประมาณ 1450px และดันแผนรายสัปดาห์ลงถึงตำแหน่งประมาณ y=2111px
- ที่ 768px กลุ่มการเงินที่มีเป้าหมายเดียวถูกยืดสูง 922px ตามกลุ่มข้างกัน
- จุดตรวจ: `src/components/planning/PlanGoalOverview.tsx:53`
- หลักฐาน: [แผน 1440px](_plan-1440.png), [แผน 768px](_plan-768.png)
- แนวแก้: แสดงสรุปและรายการจำนวนจำกัดต่อด้าน พร้อม “ดูทั้งหมด” หรือพับขยาย โดยรักษาทางเข้าทุกเป้าหมาย; ใช้ความสูงตามเนื้อหา และนำปฏิทินของช่วงเวลาที่เลือกขึ้นมาใกล้ส่วนบน
- การใส่ `items-start` อย่างเดียวลดการยืดพื้นหลัง แต่ยังไม่แก้ช่องว่างจากแถวที่สูงตามใบที่สูงที่สุด

### 5. P2 — การ์ดงานไม่มีรูปถูกยืดตามการ์ดมีรูป

- การ์ดหนึ่งมีเนื้อหาภายในประมาณ **158px** แต่ตัวการ์ดสูง **457px** เพราะอยู่แถวเดียวกับการ์ดมี cover/รายละเอียดรูป
- จุดตรวจ: `src/components/tasks/TaskCardBoard.tsx` — grid ของกลุ่มและรายการไม่มีกลุ่ม, article บรรทัด 611
- หลักฐาน: [การ์ดงาน 1440px](_tasks_mode_cards_view_planned-1440.png), [card-height-details.json](card-height-details.json)
- แนวแก้: กำหนดความหนาแน่นของการ์ดให้สม่ำเสมอ จำกัด preview ที่เหมาะสม และให้การ์ดสูงตามเนื้อหา; ถ้าเปลี่ยนระบบเรียงการ์ดต้องรักษาลำดับอ่าน/Tab และตรวจ drag & drop ใหม่
- ไม่ควรแก้ด้วยการตัดชื่อจนผู้ใช้แยกงานไม่ได้ หรือซ่อนรูป/รายละเอียดโดยไม่มีทางเปิดดู

### 6. P2 — Today จองช่อง metric เกินจำนวนข้อมูลจริง

- จุดตรวจ: `src/app/(app)/today/page.tsx:272`

- จุดตรวจ: `src/components/layout/AppShell.tsx:49`, `src/app/(app)/rescue/page.tsx:51`

## หลักเกณฑ์ container ที่เสนอ

1. หน้าที่ใช้เปรียบเทียบข้อมูลหรือจัดตาราง: กรอบกว้าง แต่แบ่งคอลัมน์จากพื้นที่ภายในจริง และมีขั้นต่ำของพื้นที่ข้อความ
2. หน้าอ่าน กรอก หรือยืนยัน: กรอบจำกัดความกว้างที่เหมาะกับเนื้อหา และให้หัวข้อ/ปุ่ม/เนื้อหาอยู่แนวเดียวกัน
3. การ์ดสรุป: สูงตามเนื้อหา จำนวนคอลัมน์ตามจำนวนรายการ ไม่จองช่องที่ไม่มีข้อมูล
4. ปฏิทินเวลา: ช่องว่างที่หมายถึงเวลาว่างยังมีความหมาย ต้องคงสัดส่วนเวลา หรือให้ผู้ใช้เลือกช่วงเวลาที่แสดงอย่างชัดเจน
5. มือถือ: ลด padding ซ้อน ใช้การเลื่อนหน้าหลัก และจัด action ลงแถวใหม่ก่อนลดความกว้างชื่อ

## ข้อจำกัดการยืนยัน

นี่เป็น layout review ของสถานะที่เปิดได้ ไม่ใช่การรับรองทุกฟังก์ชัน ทุกบทบาท ทุก modal หรือ production. ไม่ได้ทดสอบการลาก/บันทึกข้อมูลซ้ำในรอบนี้ และไม่รัน unit suite เพราะยังไม่มีการแก้ application code. หน้าพิมพ์ตรวจใน screen mode ไม่ใช่ PDF pagination.

ใช้ GitNexus สำรวจ component ร่วมและ refresh index สำเร็จผ่าน CLI (11,602 nodes / 805 flows) แต่ MCP context ยังคงรายงาน index เก่า 6 commits จึงอ้างอิง source ปัจจุบันและ browser เป็นหลักฐานสำหรับข้อค้นพบ ไม่ตีความ graph ที่ขาดข้อมูลว่าไม่มีผลกระทบ. ก่อนแก้ component ต้องทำ impact ของ index ปัจจุบันอีกครั้ง.
