## 1. เริ่มจากผู้ใช้กลุ่มเดียวที่มีปัญหาชัด

กลุ่มหลักสำหรับรอบแรกคือ **ฟรีแลนซ์และคนทำงานความรู้ชาวไทยที่มีงานส่งลูกค้าหรืองานสร้างรายได้ พร้อมภาระชีวิตที่เลื่อนไม่ได้** เช่น นักออกแบบ นักพัฒนา นักการตลาด หรือผู้ทำงานอิสระที่ต้องรับลูก ไปพบแพทย์ และจัดการค่าใช้จ่ายระหว่างวัน ไม่ได้หมายความว่าทุกอาชีพต้องใช้หน้า Sales หรือ Finance

ปัญหาหลักที่ต้องพิสูจน์มีสามข้อ:

1. เช้าวันนี้มีหลายเรื่อง แต่ไม่รู้ว่าสิ่งใดสำคัญและทำได้ทันจริง
2. เมื่อมีงานด่วนหรือประชุมเพิ่ม แผนเดิมเสีย ผู้ใช้ต้องคิดและจัดใหม่เองหลายหน้า
3. ทบทวนสัปดาห์แล้วเห็นตัวเลข แต่ยังไม่เกิดการตัดสินใจที่ทำให้สัปดาห์หน้าดีขึ้น

**สมมติฐานคุณค่า:** Kemtit ช่วยให้ผู้ใช้เลือกแผนที่พอดีกับเวลาจริง ปรับแผนโดยรักษางานสำคัญ และเปลี่ยนบทเรียนเป็นการลงมือทำรอบถัดไปได้ใน workflow เดียว

ข้อความสำหรับทดสอบ positioning: **“รู้ว่าวันนี้ทำอะไรไหว และจัดแผนใหม่ได้เมื่อชีวิตเปลี่ยน”** เป็นสมมติฐานสำหรับทดสอบ ไม่ใช่ข้ออ้างว่าคู่แข่งไม่มีหรือผู้ใช้ยอมจ่ายแล้ว

หลักฐานตลาดและข้อเทียบผลิตภัณฑ์อยู่ใน [รายงานวิจัยคู่แข่ง](planner-competitor-research-2026-09-22.md) ให้ใช้รายงานนั้นตรวจข้อความขายก่อนเผยแพร่ จุดเด่นเบื้องต้นคือการรวม capacity, recovery, review และบริบทภาษาไทยให้ต่อเนื่องกัน ไม่ถือว่าแต่ละฟีเจอร์เป็นเอกลักษณ์โดยตัวมันเอง

ข้อเทียบที่ต้องสะท้อนใน positioning: Top priorities, timeboxing, capacity planning, weekly review และ replan มีในตลาดแล้ว รายงานวิจัยตรวจแหล่งทางการครบ 9 ผลิตภัณฑ์ รวม Griply ซึ่งเชื่อม goals/tasks/habits/life areas, Todoist Ramble ที่รองรับเสียงไทย, Notion ที่ประกอบ workspace ได้ และ LINE Calendar ที่มีนัดหมายกับการแจ้งเตือน การมีผลิตภัณฑ์ LINE Calendar ไม่ได้ยืนยันว่ามี public API สำหรับเชื่อมข้อมูล; อย่าวาง integration นี้เป็น dependency จนตรวจสัญญา API ได้ ดังนั้นข้อเสนอที่นำไปทดลองคือ **ประสบการณ์รวมสำหรับคนทำงานคนเดียวในไทยที่เชื่อมงาน ชีวิต ภาระเงิน และ LINE พร้อมลดการตัดสินใจซ้ำและรักษา deadline ระหว่างปรับแผน** ยังต้องพิสูจน์ว่าทำได้ดีกว่าวิธีเดิมและผู้ใช้เห็นคุณค่า

## 3. Workflow ที่ผู้ใช้ควรสัมผัส

```text
จับเรื่องไว้ก่อน → เลือกสิ่งสำคัญ → ตรวจเวลาว่างจริง → ยืนยันแผนวันนี้
                                             ↓
                                   ทำงาน / จบงาน / บันทึกผล
                                             ↓
                    มีเรื่องแทรก → ดูแผนปรับใหม่ → ยืนยันหรือแก้เอง
                                             ↓
                               ทบทวน → เลือกงานของสัปดาห์หน้า
```

เส้นทางหลักประจำวันใช้ Today, Inbox, Plan และ Calendar ส่วน Goals, Projects, Routine, Finance เป็นบริบทประกอบ ผู้ใช้ไม่จำเป็นต้องเปิดครบทุกหน้า การเพิ่ม 21 demo screens ใช้เพื่อทบทวนขอบเขตและความเชื่อมโยง ไม่ได้หมายถึงให้ผู้ใช้ทำ 21 ขั้นตอน

ตัวอย่างสำหรับทดสอบ: ผู้ใช้มีเวลาทำงาน 09:00–17:00, พัก 1 ชั่วโมง, นัด 2 ชั่วโมง และต้องรับลูก 16:00 ระบบต้องคำนวณเวลาที่ใช้งานได้จากช่วงที่ไม่ซ้ำกัน ให้ผู้ใช้เลือกรายงานลูกค้าเป็นงานสำคัญ และอธิบายว่างานที่เหลือเกินความจุตรงไหน เมื่อมีประชุมด่วนเพิ่ม 45 นาที Rescue ต้องเสนอทางเลือกและผลกระทบต่อ deadline ก่อนผู้ใช้ยืนยัน ไม่เลื่อนวันส่งเพื่อทำให้ตัวเลขดูดี

### ข้อกำหนด UX เพิ่มเติมจากผู้ใช้: ใช้ action น้อยที่สุด โดยรักษาผลลัพธ์

หลักการคือ **บอกเจตนาครั้งเดียว → ระบบเตรียมข้อมูลและความเชื่อมโยง → ผู้ใช้ตัดสินใจเฉพาะส่วนจำเป็น → ทำต่อได้ทันที** ประสิทธิภาพต้องวัดพร้อมความถูกต้อง การลดคลิกแต่ทำให้จัดประเภทผิด เปลี่ยน deadline หรือกรอกแก้ภายหลังมากขึ้น ไม่ถือว่าผ่าน

| งานของผู้ใช้ | สิ่งที่ระบบควรเตรียม | เป้าหมายจำนวน action หลังเปิดหน้าที่เกี่ยวข้อง |
| --- | --- | --- |
| จดเรื่องหนึ่ง | แสดงข้อเสนอประเภท/วัน/เวลาในหน้าจอเดียว ใช้ default ที่แก้ได้; หากไม่มีวันให้เก็บ Inbox | พิมพ์ครั้งเดียว + บันทึก 1 ครั้ง โดยไม่บังคับเลือกโมดูลก่อน |
| จัดวันนี้ | อ่านนัดหมาย/เวลาที่เหลือ เตรียมงานสำคัญและช่องเวลา พร้อมเหตุผลและสิ่งที่ยังลงไม่ได้ | เปิดข้อเสนอ + ยืนยัน รวม 2 การกดเมื่อข้อเสนอถูกต้อง |
| ทำงานเสร็จ | อัปเดต task เดิมทุกมุมมองและคำนวณผลที่เกี่ยวข้อง | กดเสร็จ 1 ครั้ง; มี Undo โดยไม่เพิ่ม confirm dialog ปกติ |
| เวลาวันนี้ลดลง | แสดงผลกระทบและข้อเสนอปรับแผนในแผงเดียว รักษา deadline/locked appointment | กรอกเวลาที่เหลือครั้งเดียว + ยืนยัน; ตัวเลือกขั้นสูงเปิดเมื่อจำเป็น |
| ทบทวนสัปดาห์ | เติมข้อมูลจริง งานค้าง และข้อเสนอการปรับปรุงให้ก่อน | เลือกสิ่งที่จะปรับ + ยืนยันส่งเข้าแผนต่อไป; reflection text เป็น optional |

จำนวนข้างต้นเป็นเป้าหมายออกแบบ ยังไม่ใช่ผลวัดจากต้นแบบ ผู้ใช้ควรแก้รายการที่ระบบตีความผิดได้ทันทีในที่เดิม โดยไม่ถูกพาไปเริ่มใหม่

กติกาหน้าจอ: Today เป็นทางเข้าปกติ, มี primary action เด่นหนึ่งเรื่องต่อบริบท, เปิด advanced fields เมื่อขอ, ไม่บังคับ onboarding/goal hierarchy/integration ก่อนสร้างงานแรก, ใช้ inline actions และ undo กับการเปลี่ยนที่ย้อนกลับได้ ระบบต้องลดทั้งการพิมพ์ซ้ำ การสลับหน้า และจำนวนการตัดสินใจ ไม่ใช่ลดเฉพาะจำนวนคลิกที่นับได้

ก่อนยอมรับ UX ให้ทดสอบงานเดียวกันเทียบวิธีเดิม วัด task success/error rate, จำนวนการแก้ข้อเสนอ, เวลาเสร็จงาน, repeated input, navigation changes และ perceived effort หาก action ลดแต่ผลผิดหรือผู้ใช้ไม่เข้าใจสิ่งที่จะเปลี่ยน ให้แก้ข้อเสนอ/คำอธิบายก่อนเพิ่ม automation

### แนวทางหน้าตาเพิ่มเติมจากผู้ใช้

- ใช้ element ที่ออกแบบตามงานวางแผนจริง เช่นแถบจังหวะของวัน แถวงานที่ลงมือทำได้ทันที และรายการเปลี่ยนแปลงก่อน–หลังการปรับแผน ลดกล่องการ์ดและ metric ซ้ำที่ดูเหมือน dashboard ทั่วไป
- **ไม่ใช้ badge หรือกล่องสถานะที่มีแถบสีขอบด้านซ้าย** รวมถึง calendar blocks และ next-action callouts ใช้ข้อความ ไอคอนที่จำเป็น พื้นผิว และเส้นกรอบที่สม่ำเสมอแทน
- ปุ่มต้องมีรูปแบบที่ออกแบบไว้ทุกสถานะ ไม่หลงเหลือกรอบเทาเริ่มต้นของ browser; เมนู Sidebar ที่เลือกใช้ตัวอักษรเข้มและไฮไลต์บางเฉพาะใต้ชื่อเมนูตาม feedback ล่าสุด ไม่วาดสัญลักษณ์ซ้อนไอคอน ไม่ใช้พื้น pill เต็มแถวหรือขอบสีซ้าย และคง keyboard focus ที่เห็นชัด
- ยังคงอ่านภาษาไทยง่าย เป้าหมายสัมผัสชัด และแสดง action สำคัญก่อนพื้นที่ตกแต่ง ความแตกต่างของภาพต้องช่วยเข้าใจงาน ไม่เพิ่มขั้นตอนหรือทำให้ข้อมูลดูแม่นยำเกินจริง

### ประสบการณ์ครั้งแรก: มีทางเริ่มทำเสมอ

ข้อกำหนดเพิ่มเติมจากผู้ใช้คือ **เข้ามาครั้งแรกแล้วไม่พบหน้าว่างที่ต้องคิดเองว่าจะเริ่มตรงไหน** ให้ใช้หน้าเริ่มทำงานใน Today พร้อมช่องเดียว “วันนี้อยากจัดการเรื่องอะไร?” พิมพ์ข้อความของตนหรือเลือกตัวอย่างที่แก้ได้ แล้วกดสร้างงานแรก ไม่บังคับกรอกประวัติ เลือกอาชีพ สร้าง goal/project หรือเชื่อมบัญชีก่อน

หลักฐานประกอบ: [NN/g เรื่อง empty states](https://www.nngroup.com/articles/empty-state-interface-design/) แนะนำใช้พื้นที่ที่ยังไม่มีข้อมูลเพื่ออธิบายสถานะและพาเข้า task สำคัญ ส่วน [GOV.UK task list](https://design-system.service.gov.uk/components/task-list/) แนะนำลดขั้นตอนของบริการก่อนเพิ่ม checklist หลายขั้น เรานำหลักการมาปรับใช้กับ Kemtit; ยังไม่ใช่ผลทดลอง onboarding ของเรา

| จุดเริ่ม | สิ่งที่ผู้ใช้เห็น | ผลของ action แรก |
| --- | --- | --- |
| Today / Inbox / Tasks | ช่องเขียนงานหนึ่งประโยค พร้อมตัวอย่างสั้นที่เลือกแก้ได้ | สร้าง task เดิมเพียงครั้งเดียว และเห็นปลายทางในหน้าเดียว |
| Plan / Calendar | เลือกงานที่จดไว้หรือเพิ่มงาน พร้อมกรอบวันว่างที่ยังไม่อ้างว่าตรวจปฏิทินแล้ว | ผู้ใช้กำหนดช่วงเวลาของตนแล้วจึงได้ข้อเสนอ; การเชื่อมปฏิทินเป็น optional |
| Goals / Projects / Routine | ตัวอย่างเริ่มต้น 2–3 แบบและเขียนเอง; แสดงว่าเป็นคำแนะนำ | บันทึกเฉพาะแบบที่ผู้ใช้เลือก ไม่สร้างชุดข้อมูลที่ต้องตามลบ |
| Finance / Sales / Entries | ช่องบันทึกรายการแรกและคำอธิบายสิ่งที่จะได้เห็น | สร้างรายการจริงจากค่าที่ผู้ใช้กรอก ไม่มีรายได้หรือบิลตัวอย่างปะปน |
| Reviews / Insights | คำถามตั้งต้น “สัปดาห์หน้าจะให้เวลากับอะไร?” และแสดงข้อมูลขั้นต่ำที่ต้องมี | บันทึกเจตนาหรืองานต่อไปได้ทันที โดยไม่สร้างกราฟหรือสรุปประสิทธิภาพที่ไม่มีหลักฐาน |

โหมดสำรวจตัวอย่างเป็นทางเลือกรองและมีป้ายชัดเจน แยกจากพื้นที่เริ่มใช้ใหม่ ตัวอย่างไม่เข้ารายงาน ไม่สร้างการเตือน และไม่ย้ายเข้า workspace จริงอัตโนมัติ เมื่อทำงานหมดให้แสดงความสำเร็จและทางเลือกพัก/วางวันถัดไป ไม่ย้อนกลับเป็นข้อความเหมือนยังไม่เคยเริ่ม ถ้า filter ไม่พบผลให้แก้ filter; ถ้าข้อมูลโหลดผิดพลาดให้ retry และเก็บ draft ไม่ปิดบังเป็น first-use state

เกณฑ์รับงาน: บัญชีใหม่เริ่มงานแรกได้โดยไม่เปิด Settings; ไม่ต้องพิมพ์งานเดิมซ้ำเพื่อวางแผน; refresh ไม่สร้าง starter ซ้ำ; ลบงานสุดท้ายแล้วยังมีทางไปต่อ; ไม่มีสถิติปลอม เป้าทดลองคือให้ผู้ใช้สร้างสิ่งที่ตั้งใจทำรายการแรกได้ภายใน 60 วินาที โดยไม่ต้องมีผู้สอน ตัวเลขนี้เป็นเป้าทดสอบ ไม่ใช่ผลที่ยืนยันแล้ว

## 4. กติกาข้อมูลและการตัดสินใจที่ต้องตกลงก่อนลงโค้ด

### 4.1 วันทำงานกับ deadline

- `planned_date` หมายถึงวันที่ผู้ใช้ตั้งใจลงมือ ส่วน deadline หมายถึงกำหนดที่ต้องเสร็จ อาจไม่มี deadline ได้
- เปลี่ยนแผนแล้ว deadline ต้องคงเดิม เว้นแต่ผู้ใช้เลือกแก้ deadline โดยตรง
- ข้อมูล `due_date` เดิมมีความหมายปะปน ต้องใช้ migration แบบเพิ่ม field ก่อน เก็บค่าดั้งเดิม และให้ผู้ใช้เห็นการตีความ ไม่แปลงทุกแถวเป็น hard deadline โดยอัตโนมัติ
- งานที่แบ่งหลายช่วงใช้ task เดิมผูกหลาย blocks; การครบหนึ่ง block ไม่เท่ากับ task เสร็จโดยอัตโนมัติ

### 4.2 เวลาว่าง ความจุ และค่าประเมิน

- คำนวณจาก working windows ของวัน ลบ union ของ busy commitments/พัก/ขอบเขตเวลาที่ผู้ใช้เลือก แล้วค่อยวางงานในช่องที่เหลือ
- แยก “เวลาที่ลง block แล้ว”, “เวลางานที่ยังไม่มีที่ลง”, “เวลาว่าง” และ “เวลาที่เกิน” ไม่บวก estimate กับ linked block ซ้ำ
- รายการ external event ที่ถูก import ซ้ำต้อง deduplicate ด้วย provider identity; all-day event ให้ผู้ใช้เลือกว่ากันทั้งวันหรือเป็นข้อมูลประกอบ
- Default estimate ต้องติดป้ายว่าประเมิน เช่น “ยังไม่ได้ระบุเวลา · ใช้ 30 นาทีชั่วคราว” ห้ามแสดงเป็นเวลาจริง
- วันในอดีต/เวลาที่ผ่านไปแล้ว, block ข้ามเที่ยงคืน, timezone และเหตุการณ์ที่ยกเลิกต้องมี semantics ชัด การแสดงตาม timezone ต้องไม่เปลี่ยน identity ของ recurrence
- ถ้า calendar sync เก่าหรืออ่านล้มเหลว ให้แสดงความไม่แน่นอนและเวลาซิงก์ล่าสุด ไม่สรุปว่าช่วงนั้นว่าง

### 4.3 Identity และความสอดคล้อง

- Task, goal, project และ event ใช้ canonical record เดียวข้ามทุกหน้า ไม่ copy เมื่อ promote จาก inbox หรือเมื่อ review นำงานไปสัปดาห์หน้า
- งานซ้ำระบุทั้ง series/task ID และ immutable source occurrence date; `scheduled_date` เป็นวันที่ย้ายไป การย้ายสองรอบมาวันเดียวกันต้องไม่กลืนกัน
- Daily priorities และ blocks ต้องอ้าง occurrence ที่ตั้งใจเลือกได้ ไม่ใช้ task ID อย่างเดียวเมื่อมีหลาย occurrence
- Move, skip, complete, archive ต้องกำหนดผลต่อ linked blocks อย่างชัดเจนและทำ atomic เมื่อจำเป็น ป้องกัน stale client เขียนทับแผนใหม่แบบเงียบ ๆ

### 4.4 Replan ที่ควบคุมได้

- เริ่มจากกฎ deterministic: รักษา locked blocks และ deadline, ให้ top priorities มาก่อน, ใช้ duration และ free windows, จากนั้นเสนอรายการที่ควรเลื่อน
- Preview ต้องแสดง “คงไว้/ย้าย/ยังลงไม่ได้/เสี่ยงส่งไม่ทัน” พร้อมเหตุผลแต่ละข้อ ให้แก้เป็นรายรายการได้
- Confirm เป็นการกระทำชัดเจน; หลังสำเร็จมี undo ที่คืน snapshot หรือ compensating changes ตาม version ที่ปลอดภัย ถ้ามีการแก้เพิ่มแล้ว undo ไม่ได้ทั้งหมดต้องอธิบาย ไม่ทับข้อมูลล่าสุด
- ไม่มีที่ลงให้บอกว่าแผนทำไม่ทันและเสนอให้ผู้ใช้ลด scope, เปลี่ยนลำดับ หรือคุยเรื่อง deadline ไม่ยัดงานทับเวลาพักหรือเวลานัด
- LLM ไม่ใช่ dependency ของ P0–P2 หากเพิ่มภายหลังใช้เพื่อช่วยตีความ/อธิบาย โดยการบันทึกจริงยังผ่าน validation และ confirmation ชุดเดียวกัน

### 4.5 Review ต้องเกิดการกระทำต่อ

- เลือกสัปดาห์และโหลด record ของสัปดาห์นั้น แยก review ก่อนหน้าเป็น reference
- แยก outcome, งานเสร็จ, ความสม่ำเสมอ และเวลาที่วางแผนไว้ ไม่เรียก planned time ว่า actual work
- ให้เลือกงานค้างที่จะทำต่อ/เลื่อน/หยุด แล้วเลือกลำดับสำคัญรอบใหม่; link ไป actual next-week plan และรักษา task ID เดิม
- ถ้ายังไม่มี actual duration อย่าคำนวณ estimate accuracy แบบสร้างตัวเลขขึ้นมา เพิ่มการบันทึก optional ก่อนใช้ insight ดังกล่าว

### 4.6 เข้าสู่ระบบด้วย Google

เพิ่มตามคำขอผู้ใช้วันที่ 22 กันยายน 2026: หน้า Login ต้องมี “เข้าสู่ระบบด้วย Google” ควบคู่กับอีเมล ให้กลับมายังหน้าที่ตั้งใจเปิดหลังสำเร็จ และกลับมาเลือกวิธีอื่นได้เมื่อยกเลิก/ล้มเหลว ต้นแบบจำลองขั้นตอนเท่านั้น ไม่ขอรหัสผ่าน Google และไม่สร้าง session จริง

ระบบปัจจุบันใน `src/core/auth/actions.ts` ใช้อีเมล OTP และ `nextRouteFor` / `safeInternalPath` อยู่แล้ว การเพิ่ม Google ใน P1 ต้องใช้ Supabase Auth เดิมและรักษา onboarding gate เดิม: ตั้งค่า provider และ redirect allowlist, เริ่ม OAuth, แลก code ผ่าน callback ของการเข้าสู่ระบบ และตั้ง session cookie ก่อนนำทาง อ้างอิง [Supabase Google Auth](https://supabase.com/docs/guides/auth/social-login/auth-google)

การเข้าสู่ระบบกับการเชื่อม Google Calendar เป็นคนละการอนุญาต ห้ามบังคับขอสิทธิ์อ่าน Calendar ตอน sign in; ให้ผู้ใช้เลือกเชื่อมภายหลัง ใช้รูปแบบปุ่มและเครื่องหมาย Google ตาม [Google branding guidelines](https://developers.google.com/identity/branding-guidelines)

เกณฑ์รับงาน: ผู้ใช้ใหม่/ผู้ใช้เดิมไปหน้าถูกต้อง, ยกเลิก/หมดอายุ/ใช้ callback ซ้ำมีทางลองใหม่, ไม่ redirect ออกนอกปลายทางที่อนุญาต, session และ RLS ระบุตัวผู้ใช้จริง, อีเมล OTP ยังใช้ได้, ไม่เพิ่มสิทธิ์ Calendar โดยอัตโนมัติ และไม่บันทึก token ลง log/localStorage ของต้นแบบ

### 5.1 State contract ที่ใช้ทุกหน้า

ทุกหน้าต้องออกแบบหกสถานะต่อไปนี้ก่อนถือว่าพร้อมพัฒนา ไม่ใช่แค่ happy path ใน mockup:

- **Done/success:** ยืนยันผลที่สำเร็จและสิ่งที่จะทำต่อ; mutation สำเร็จจริงก่อนแสดง saved, มี undo สำหรับการเปลี่ยนแผนที่รองรับ
- **Empty:** แยกว่าไม่มีข้อมูลจริง, ยังไม่ได้ตั้งค่า หรือ filter ไม่พบ พร้อม CTA เดียวที่ตรงสาเหตุ ไม่ seed ข้อมูลตัวอย่างเป็นข้อมูลจริง
- **Loading:** skeleton เฉพาะพื้นที่ที่กำลังอ่าน; ปิด submit ซ้ำอย่างเหมาะสม และรักษา input/รายการที่อ่านได้แล้ว
- **Error:** บอกว่าอ่านหรือบันทึกส่วนใดไม่สำเร็จ มี retry โดยไม่สร้างรายการซ้ำ ไม่แทน read error ด้วย “ไม่มีงาน”
- **Offline:** แสดงข้อมูลล่าสุดพร้อมเวลา; draft เก็บ local ได้ถ้าออกแบบไว้ แต่ต้องติด pending และไม่บอกว่าบันทึก server แล้ว การยืนยัน replan ข้ามหลายรายการให้รอ online
- **Permissions:** ไม่มีสิทธิ์ใน record ให้ตอบปลอดภัย; integration ที่ไม่อนุญาตยังใช้ manual planning ได้ ไม่วนขอสิทธิ์และไม่ expose ข้อมูลจาก record อื่น

### 5.2 จุดเฉพาะของแต่ละหน้าในหกสถานะ

ตารางนี้เป็น acceptance specification ของ production ไม่ใช่คำอ้างว่าต้นแบบจำลองทุก failure mode ได้แล้ว; `loading/error/offline` ใช้สัญญาร่วมด้านบนและรายละเอียดในคอลัมน์สุดท้าย

| หน้า | Done / Empty | Permissions และกรณี loading/error/offline ที่ต้องทดสอบเพิ่ม |

| Today | ทำงานสำคัญเสร็จแล้วเสนอพักหรือเลือกต่อ / ไม่มีงานให้ capture หรือวางวันพัก | calendar อ่านไม่ได้ต้องไม่แสดง free time แบบมั่นใจ; offline ไม่ยืนยัน capacity สด |
| Plan | แผนที่เลือกถูกผูกกับ task เดิม / ไม่มี goal ก็วางงานได้ | โหลดช่วงใหม่คงช่วงเดิมจนพร้อม; ไม่ให้ stale request ทับช่วงล่าสุด |
| Calendar | ย้าย block สำเร็จพร้อม undo / ไม่มีนัดให้วาง block แรก | OAuth denied ใช้ manual ได้; expired sync แสดงข้อมูลเก่า; conflict save รักษาฟอร์ม |

## 6. ลำดับพัฒนาแบบพึ่งพากัน

ไม่มีการให้วันส่งมอบจากจำนวนหน้าต้นแบบ ระยะด้านล่างใช้ exit criteria เป็นตัวตัดสิน หลัง P0 และ usability pilot จึงประเมิน effort จาก implementation จริงและข้อมูลที่ต้อง migrate

| ระยะ | สิ่งที่จะได้ | ลำดับ dependency | Exit criteria |
| --- | --- | --- | --- |
| **P0 — Correctness และ baseline** | แก้ review ผิดสัปดาห์, block lifecycle, read-error states; ตกลง deadline/planned semantics, baseline tests และสิทธิ์ asset | ตรวจ source/schema ปัจจุบัน → impact เฉพาะส่วน → migration/contract แบบ additive → tests; ตรวจชุด asset ที่จะเผยแพร่ตาม [นโยบาย](asset-usage-policy.md) | ไม่มี silent deadline change; ข้อมูลผิดพลาดไม่แสดงเป็นว่าง; ย้าย/undo แล้ว task/block สอดคล้อง; required CI checks ผ่านหรือระบุ blocker ที่แก้ก่อน release; ฟอนต์/ไอคอนมี provenance และ notice ครบ พร้อมแยกสถานะเครื่องหมายการค้า |
| **P1 — Daily plan ที่ต่อกัน** | Google/อีเมลเข้าใช้ → Capture → priority → capacity/free windows → calendar → complete; Today เป็นหน้าหลัก | P0 identity/date contract → shared availability → Today/Plan/Calendar ใช้ผลเดียวกัน → goal/project context; Google ใช้ Auth เดิมตามข้อ 4.6 | ผู้ใช้สร้างแผนวันนี้และแก้ความจุเกินได้โดยไม่พิมพ์งานซ้ำ; capacity อธิบายได้และไม่ double count; Google ยกเลิก/ล้มเหลวแล้วยังใช้อีเมลได้ |
| **P2 — Recovery และ Review** | Rescue preview/confirm/undo, optional Focus, review เลือกแผนสัปดาห์หน้า, insights จากหลักฐาน | P1 availability/versioning → deterministic proposal → transactional apply/undo → review carryover → insight | แผนใหม่รักษา locks/deadlines, บอกงานที่ลงไม่ได้; review เปลี่ยน next-week plan จริง; stale state/concurrent edits ไม่หาย |
| **P3 — Thai capture และ LINE** | ลดแรงเสียดทานสำหรับบริบทไทยและการกลับมาใช้งาน | ผล pilot P1/P2 → ทดสอบภาษาไทย → preview interpretation → integration opt-in → delivery observability | ผู้ใช้ตรวจและแก้วันที่/เวลา/ประเภทก่อน save ได้; LINE ตั้งเวลา/ความถี่/หยุดได้; denied/offline/retry ไม่สร้างข้อมูลหรือข้อความซ้ำ |

P3 ควรเริ่มจากภาษาไทยที่มีขอบเขต เช่น “ทำใบเสนอราคา พรุ่งนี้ 30 นาที” พร้อม preview วันที่จริง ก่อนภาษาธรรมชาติเปิดกว้าง ส่วน LINE ทดสอบ opt-in daily brief/เตือน review ก่อน workflow ที่เขียนข้อมูลกลับ ไม่ใช้จำนวน notification เป็นตัววัดความสำเร็จ

คง Next.js, TypeScript, Supabase/RLS, Server Actions และ modular monolith เดิม ใช้ core service/domain เดียว ไม่เพิ่ม planner อีกระบบข้างของเดิม ไม่มี broad rewrite, dependency ใหม่ หรือ paid LLM เป็นเงื่อนไขของคุณค่ารอบแรก

## 7. Acceptance scenarios ที่ต้องผ่านก่อนใช้กับข้อมูลจริง

1. **วันแน่น:** working windows 8 ชั่วโมง, busy union 3 ชั่วโมง, task demand 6 ชั่วโมง ต้องเห็นเกิน 1 ชั่วโมง; event ซ้อน event ไม่ลบเวลาซ้ำ; linked block ของ task ไม่นับสองครั้ง
2. **วันส่งกับวันทำ:** งานตั้งใจทำอังคาร ส่งศุกร์ เมื่อย้ายไปพุธ deadline ยังศุกร์; rescue ต้องเตือนหากย้ายเกินศุกร์
3. **งานซ้ำย้ายชนรอบ:** ย้าย occurrence จันทร์ไปอังคารซึ่งมีรอบธรรมชาติอยู่แล้ว ต้องเห็นสองรอบ, เลือก priority/complete/block ได้แยกกัน และประวัติเดิมคงอยู่
4. **นัดแทรก:** เพิ่ม busy event ทับ block ต้องมี conflict ที่มองเห็นพร้อมทางเลือก ผู้ใช้ยืนยัน replan แล้วทุก view เห็นสถานะเดียวกัน; locked commitment ไม่ถูกย้าย
5. **แก้เวลาผิด:** block 09:00–10:00 แก้เป็น 10:00–11:00 สำเร็จแล้ว undo กลับได้ หากอีกอุปกรณ์แก้ต่อแล้วระบบต้องแจ้ง conflict ก่อนคืนค่า
6. **ไม่มีทางลงงาน:** task 90 นาทีแต่มีแต่ช่องว่าง 30 นาที และ task ไม่อนุญาตแบ่ง ต้องแจ้งยังลงไม่ได้ ไม่แอบแบ่งหรือวางทับนัด
7. **Review คนละสัปดาห์:** มี review สัปดาห์ A แต่เปิด B ต้องไม่เอาคำตอบ A มาเป็น B; carryover ใช้ task ID เดิมและลิงก์ไปสัปดาห์ C ที่ตั้งใจไว้
8. **ข้อมูลอ่านไม่ได้:** tasks/calendar/profile request fail ต้องเห็น error/retry และข้อมูลที่ยังเชื่อถือได้ ไม่แสดง “วันนี้ว่าง” หรือ capacity ปลอม
9. **สิทธิ์และ integration:** ใช้แอปได้เมื่อไม่เชื่อม Google/LINE; revoked provider แจ้ง reconnect โดยรักษา manual data; ไม่อ่าน/แก้ task ของผู้ใช้อื่น
10. **Retry และหลายอุปกรณ์:** capture/confirm ซ้ำด้วย operation เดิมเกิดผลครั้งเดียว; stale replan ตรวจ version; refresh ระหว่าง save ไม่ทำ task, entry, event หรือ notification ซ้ำ
11. **มือถือและ accessibility:** keyboard/focus order ชัด, screen reader รู้ saved/error, touch target ใช้งานได้, ข้อความไทยไม่ล้น, sticky controls ไม่บัง undo หรือ save
12. **หลักฐานเวลา:** planned duration, estimated duration และ actual duration แยกกัน; ยังไม่มี actual ให้บอกไม่ทราบ ไม่สรุปประสิทธิภาพจาก planned blocks

Unit tests เน้น domain semantics/free-window union/priority/occurrence/version rules; integration tests เน้น RLS, transactions, idempotency และ apply/undo; E2E เน้น Capture → Plan → Conflict → Rescue → Review โดยมี failure cases ที่สำคัญ ไม่เขียน test เพียงยืนยันว่าปุ่มเรียก helper เดิม

## 8. Pilot เพื่อเลือกสิ่งที่จะลงทุนต่อ

รับผู้ใช้ 5–8 คนในกลุ่มหลักที่มีงานรับเงินหรือ deliverable และภาระชีวิตจริง ทดลองสองสัปดาห์โดยสมัครใจ ใช้สัปดาห์แรกบันทึก baseline/รูปแบบการทำงาน แล้วทดสอบ core workflow และการปรับแผนในสถานการณ์จริง พร้อมสัมภาษณ์สั้นและดูการใช้งานต้นแบบก่อน production หากเก็บข้อมูลจากต้นแบบให้ใช้ข้อมูลตัวอย่างหรือข้อมูลที่ผู้ใช้ยินยอม ไม่ใส่รายละเอียดลูกค้าที่เป็นความลับ

จำนวนตัวอย่างนี้ช่วยพบความสับสนและตรวจสมมติฐานเชิงคุณภาพ **ไม่ใช่หลักฐานเชิงสถิติว่า Kemtit ทำให้ productivity เพิ่ม** เปรียบเทียบ within-person อย่างระมัดระวัง เพราะภาระงานแต่ละสัปดาห์ต่างกัน

| ตัวชี้วัด | นิยามที่ไม่ชวนตีความเกิน | สิ่งที่ต้องเรียนรู้ |
| --- | --- | --- |
| Time to next action | เวลาจากเปิด Today จนผู้ใช้เลือกงานที่จะลงมือ ไม่ใช่เวลาโหลดหน้า | ผู้ใช้ตัดสินใจง่ายขึ้นหรืออ่านข้อมูลนานขึ้น |
| Planning effort | เวลาที่ใช้ capture/plan/replan รวมต่อวัน พร้อมถามว่ารู้สึกคุ้มหรือไม่ | ระบบลดภาระหรือเพิ่มงานดูแล planner |
| Priority follow-through | งานสำคัญที่ผู้ใช้ยืนยันแล้วเสร็จ พร้อมนับการเปลี่ยน/ยกเลิกอย่างเปิดเผย | ความสำเร็จเกิดจากเลือกเหมาะสม ไม่ใช่ลบงานยากออกจากตัวหาร |
| Rescue usefulness | เหตุที่ต้อง replan, ยอมรับ/แก้/ปฏิเสธข้อเสนอ, เวลาปรับ, เหตุที่ undo | คำแนะนำตรงชีวิตจริงและผู้ใช้ควบคุมได้หรือไม่ |
| Review-to-action | review ที่ผู้ใช้ยืนยันการตัดสินใจและมี task/plan จริงในสัปดาห์ถัดไป | review เปลี่ยนพฤติกรรมหรือเป็นฟอร์มเพิ่ม |
| Trust/correctness incidents | เวลาซ้ำ, deadline เปลี่ยนผิด, รายการหาย/ซ้ำ, capacity ไม่ตรง พร้อม severity | ต้องหยุดปรับ UX เพื่อแก้ฐานข้อมูลหรือไม่ |
| Continued use and willingness | ผู้ใช้กลับมาเองกี่วัน เหตุผลที่หยุด และยอมเลือกใช้แทนวิธีเดิมหรือไม่ | คุณค่าต่อเนื่องและความสนใจจ่ายเงิน โดยไม่เอาคำชม UI มาแทน |

ตัดสินใจหลัง pilot: เก็บ flow ที่ช่วยเลือก/ปรับงานได้จริง ลดหน้าหรือขั้นที่ถูกข้ามบ่อย ตรวจปัญหาความน่าเชื่อถือก่อนเพิ่ม insight/AI ถ้า users ยังต้องจัดงานหลักในแอปอื่นทุกวัน ให้หาสาเหตุก่อนขยายกลุ่มเป้าหมายหรือทำ integrations หลายรายพร้อมกัน
