# วิเคราะห์ UI/UX Kemtit จากภาพอ้างอิง — 9 ตุลาคม 2026

สถานะ: ข้อเสนอเพื่อออกแบบ ยังไม่ได้เปลี่ยน UI หรือพฤติกรรมแอป

ข้อกำหนดจากผู้ใช้: **ห้ามคัดลอกงานออกแบบจากภาพอ้างอิง** ใช้ภาพเพื่อวิเคราะห์ปัญหาและหลักการใช้งาน แล้วออกแบบโครงหน้า องค์ประกอบ ภาพ และข้อความของ Kemtit ขึ้นเอง ไม่ทำสำเนาหน้าจอหรือดัดแปลงเพียงเปลี่ยนสี/ชื่อ และไม่นำ asset จากภาพต้นแบบเข้าแอป

แผนส่งมอบที่ต่อยอดจากคำถามเรื่องการวางแผนชีวิต ภาพรวม และ wizard: [Life Planning UX Delivery Plan](2026-10-09-life-planning-ux-delivery-plan.md)

คำขอเพิ่มเติม: รวม Drag & Drop และทั้ง 7 ข้อไว้ในรุ่นแรก หัวข้อ 6.1–6.2 และระยะ 2 ของแผนส่งมอบ ได้แก่ การ์ด Task, ลากลงปฏิทิน, วันเวลาอัปเดตในการ์ด, รูปแรกเป็น cover/title fallback, ทุกประเภทอุปกรณ์, กลุ่มแบบ iPhone และ research/usability รายละเอียดใน [ข้อกำหนดการ์ด ปฏิทิน และกลุ่ม](2026-10-09-task-cards-calendar-groups.md)

## ข้อสรุป

ใช้แนวทางเดิม Calm Operational Planner ให้ชัดขึ้น: อ่านง่ายเหมือนสมุดวางแผน ลงมือทำได้เร็ว และเห็นเวลาเมื่อจำเป็น โดยสกัดหลักการเรื่องลำดับข้อมูลและความเป็นส่วนตัวจากภาพ 5 และ 7 ศึกษาการสื่อเวลา/ภาระงานจากภาพ 1 และ 6 และแนวคิดวงจรวางแผน–ทบทวนจากภาพ 4 แล้วออกแบบโครงหน้าและภาษาภาพของ Kemtit เอง

ปัญหาหลักที่พบในรอบนี้คือความสำคัญของข้อมูลและจำนวนทางเลือกบนหน้า มากกว่าการขาดสีหรือฟีเจอร์ ควรเริ่มจาก Today → Plan → Calendar ก่อนเพิ่มมุมมองโครงการขั้นสูง

## หลักฐานและขอบเขต

- อ่านภาพแนบทั้ง 7 ภาพเป็นข้อมูลอ้างอิง ภาพ 4 เป็นอินโฟกราฟิกแนวคิด ไม่ใช่หลักฐานว่า Kemtit หรือบริการที่กล่าวถึงมีความสามารถเหล่านั้น
- ตรวจหน้า local `/today`, `/plan` และ `/calendar` ผ่าน Chrome ด้วยบัญชีทดสอบที่เพิ่งสร้าง ข้อมูลว่าง และบทบาทผู้ขาย/ร้านค้า
- ข้อค้นพบด้านการจัดวางเป็นการตรวจ desktop ครั้งนี้ ยังไม่ได้ทดสอบผู้ใช้จริง ข้อมูลจำนวนมาก หรือ responsive รอบใหม่
- อ่าน `docs/Kemtit_UI_Optimization_Implementation_Plan.md`, `docs/plans/2026-10-08-sidebar-consolidation.md` และ `docs/qa/full-system-2026-10-08/QA-REPORT.md` ผล QA เดิมไม่ใช่ผลทดสอบข้อเสนอฉบับนี้
- เรียก GitNexus query เรื่อง Today/planning/calendar ได้คำจำกัดความเกี่ยวกับ capacity/availability แต่ไม่มี execution flow ที่ตอบคำค้นนี้ จึงไม่ใช้ผลดังกล่าวสรุปว่าเปลี่ยนระบบได้โดยไม่มีผลกระทบ

## วิเคราะห์ภาพอ้างอิง

| ภาพ | สิ่งที่นำมาใช้ได้ | ข้อจำกัด/สิ่งที่ควรปรับให้เหมาะกับ Kemtit |
| --- | --- | --- |
| 1 — Gantt และ task register | แถบควบคุมรวมกัน เส้นเวลาเทียบกับรายการ งานสัมพันธ์กับช่วงเวลา และเปรียบเทียบแผนกับผล | เหมาะกับโครงการที่มีหลายขั้นตอน ตัวอักษรและตารางหนาแน่นเกินไปสำหรับหน้าเริ่มต้น การคำนวณ critical path/dependency เป็นงานระบบเพิ่มเติม |
| 2 — ตัวอย่างพิมพ์หน้าแผน | แยกการส่งออกจากการแก้ไข และเลือกช่วงเวลาสำหรับรายงาน | ภาพมีพื้นที่ว่างมากและตัวหนังสือเล็ก แต่ยังสรุปสาเหตุของระบบต้นทางไม่ได้ ควรออกแบบเอกสารพิมพ์เฉพาะ แทนย่อหน้าเว็บทั้งหน้า |
| 3 — ตัวอย่างพิมพ์ทะเบียนงาน | ใช้ตารางสรุปสถานะ ความคืบหน้า และผู้รับผิดชอบ | ใน PDF ควรใช้ข้อความ/เปอร์เซ็นต์แทน slider และไม่แสดงเมนูแก้ไข หากคอลัมน์มากให้แยกส่วนหรือใช้แนวนอน |
| 4 — Production Control | วงจรแผน → ผลจริง → ปัญหา → การตัดสินใจ → ทบทวน | แปลงเป็นคำถามสำหรับชีวิต/งานรายบุคคล ไม่ควรเพิ่ม stock, machine, SKU หรือ AI assistant ทั้งชุดจากภาพเดียว |
| 5 — Digital Planner | โทนอ่อน หมวดรายวัน/สัปดาห์/เดือน และพื้นที่บันทึกที่รู้สึกเป็นของผู้ใช้ | ใช้ระบบพื้นที่และจังหวะการอ่าน ส่วนภาพหมี สติกเกอร์ และฟอนต์ตกแต่งไม่จำเป็นต่อหน้าทำงาน ห้ามใช้ทรัพย์สินภาพต้นแบบเป็นแบรนด์ Kemtit |
| 6 — Resource schedule | มองช่วงเวลาชนกันและภาระงานเทียบกับเวลาว่างได้รวดเร็ว | สำหรับผู้ใช้คนเดียวให้เริ่มจากตารางเวลาของตนเอง การจัดทีม/สิทธิ์/ทรัพยากรเป็นขอบเขตใหม่ ต้องประเมินแยก |
| 7 — Weekly cards | งานอ่านง่าย เพิ่มงานใกล้วันที่ต้องการ และเป้าสัปดาห์อยู่ข้างรายการ | ถ้ามี 7 คอลัมน์แคบบนจอเล็กจะอ่านยาก ใช้วันเลือกได้พร้อมรายการบนมือถือ ใช้สีอ่อนอย่างจำกัดและไม่รวมเสาร์–อาทิตย์จนข้อมูลหาย |

## โครงร่างหน้าวันนี้ที่เสนอ

```text
วันนี้                         วันที่        + เพิ่ม
งานเสร็จ / ทั้งหมด     นัดถัดไป     เวลาที่จัดไว้

┌──────────────────────────────────┬────────────────────────┐
│ สิ่งสำคัญวันนี้ สูงสุด 3 รายการ   │ ตารางเวลาวันนี้         │
│ งานวันนี้                        │ นัดหมาย / ช่วงเวลางาน   │
│ งานค้าง แสดงเมื่อมี               │ + จัดเวลา              │
│ + เพิ่มงาน                       │                        │
├──────────────────────────────────┴────────────────────────┤
│ กิจวัตรแบบย่อ  •  โน้ต  •  เรื่องที่ต้องใส่ใจเมื่อมีจริง     │
└───────────────────────────────────────────────────────────┘
ตัวเลือกเพิ่มเติม: ตั้งค่าแผน / วิธีใช้ / ข้อมูลประกอบ
```

โครงนี้เป็นสมมติฐานสำหรับ mockup ไม่ได้กำหนดตัวเลขข้อมูลตัวอย่างให้แสดงในระบบจริง

- Desktop: พื้นที่งานประมาณ 60% และตารางเวลาประมาณ 40% ทดลองกับข้อความไทยยาวก่อนกำหนดสัดส่วนจริง
- Tablet: เปลี่ยนเป็นคอลัมน์เดียวเมื่อพื้นที่เริ่มบีบชื่อรายการ ไม่บังคับให้เหมือน desktop
- Mobile: สิ่งสำคัญและรายการวันนี้มาก่อน ให้ตารางเวลาเข้าถึงใกล้กัน; คงเมนูหลัก Today / Plan / + / Insights / More ตามสัญญาเดิม
- เมื่อมีงาน: แต่ละแถวแสดงชื่อ สถานะ และวัน/เวลาที่เกี่ยวข้อง รายละเอียดอื่นเปิดเมื่อเลือก
- เมื่อไม่มีงาน: แสดงทางเริ่มต้นหลักหนึ่งทาง โดยไม่สร้างข้อมูลสมมติเพื่อเติมหน้า
- งานไม่มีเวลาไม่ถูกยัดลงตารางโดยอัตโนมัติ งานเลยกำหนดไม่เปลี่ยนกำหนดส่งเพียงเพราะเลือกทำวันนี้

## หน้าที่ของแต่ละหน้า

1. **Today — ลงมือทำ:** วันนี้ควรเริ่มอะไร งานใดสำคัญ นัดถัดไปเมื่อไร
2. **Plan — วางทิศทาง:** เป้าปี → เดือน → สัปดาห์ และงานที่ช่วยให้เป้าคืบหน้า
3. **Calendar — จัดเวลา:** นัดหมาย ช่วงเวลางาน และสิ่งที่ทับซ้อน; แยกงานตามกำหนดออกจากนัดที่มีเวลาจริง
4. **Tasks — จัดรายการ:** ค้นหา กรอง จัดการงานทั้งหมด โดยไม่เพิ่มข้อมูลซ้ำกับมุมมองอื่น
5. **Reviews/Insights — ทบทวน:** สิ่งที่ตั้งใจไว้ เทียบกับสิ่งที่ทำได้ พร้อมทางกลับไปปรับแผน

หากทำมุมมองการ์ดรายสัปดาห์แบบภาพ 7 ให้เป็นการแสดงข้อมูลชุดเดิมในหน้าที่มีหน้าที่ชัดเจน ใช้ Plan สำหรับบริบทเป้าหมาย และ Calendar สำหรับบริบทวันที่/เวลา หลีกเลี่ยงสร้างกระดานอีกชุดที่ต้องกรอกข้อมูลซ้ำ

## ภาษาภาพและการโต้ตอบ

- คงม่วงของ Kemtit เป็นสีหลัก พื้นหลังกลางอ่อนและพื้นผิวขาว เพิ่มสีอ่อนเฉพาะเมื่อมีความหมาย
- ลดกรอบ เงา และการ์ดซ้อน ให้หัวข้อ ช่องว่าง และเส้นแบ่งช่วยจัดข้อมูล
- รักษาข้อกำหนดเดิมเรื่องไม่ใช้แถบสีด้านซ้ายหรือสีแรงต่างกันทุกการ์ด
- เริ่มทดลองข้อความเนื้อหาประมาณ 16px และปุ่มสัมผัสประมาณ 44px เป็นเป้าหมายการออกแบบ พร้อมตรวจ contrast, focus, zoom และชื่อที่โปรแกรมอ่านหน้าจอใช้
- ข้อความไทยต้องตัดบรรทัดได้ ปุ่มอังกฤษต้องไม่ทำให้ layout ล้น และไม่ตัดชื่อรายการจนเลือกผิด
- เมนูย่อยหรือแผงแก้ไขต้องคืน focus เมื่อปิด; การลากย้ายต้องมีปุ่ม/คีย์บอร์ดทำสิ่งเดียวกันได้
- การเปลี่ยนสถานะ/ย้ายวันต้องแสดงผลบันทึกและ Undo ที่สอดคล้องกับระบบเดิม
- ใช้ Quick Capture เดิม: พิมพ์ → ตรวจสิ่งที่จะเพิ่ม → ยืนยัน → เชื่อมข้อมูล ห้ามลดขั้นตอนด้วยการข้ามการยืนยันข้อมูลสำคัญ

| สรุปเช้า/ทบทวน | วันนี้มีอะไรสำคัญและต้องตัดสินใจอะไร | เริ่มจากข้อมูลจริงและกฎคำนวณที่อธิบายได้ ยังไม่ต้องเพิ่ม AI provider |

ตัวชี้วัดเวลาใช้จริง, baseline ของโครงการ, critical path, workload ของทีม และ AI อธิบายสาเหตุ ไม่ถือว่าเป็นเพียงการเปลี่ยน UI ต้องตรวจโมเดลข้อมูลและขอบเขตผลิตภัณฑ์แยกก่อน

## วิธีวัดและ QA ที่เสนอ

ยังไม่มีค่าฐานการทดสอบผู้ใช้ในรอบนี้ จึงไม่อ้างเปอร์เซ็นต์ที่ดีขึ้น

- ให้ผู้ใช้ลองเพิ่มงาน เลือก 3 สิ่งสำคัญ จัดเวลา เลื่อนวัน และทำเครื่องหมายเสร็จ วัดเวลา จำนวนการย้อนกลับ และข้อผิดพลาดเทียบก่อน/หลัง
- ตรวจสภาพไม่มีข้อมูล มีรายการจำนวนมาก ชื่อยาว งานเกินเวลา งานซ้ำประจำ และงานเลยกำหนด
- ตรวจ loading/error/empty เป็นคนละสถานะ รวมถึงบันทึกล้มเหลวและ retry โดยไม่สร้างซ้ำ
- ตรวจ browser reload, URL view/date/scope, keyboard, focus, screen-reader labels และไม่มี horizontal overflow ที่ 1440/768/390/360px
- เมื่อลากงานต้องชัดว่าเปลี่ยนวันที่วางแผน กำหนดส่ง หรือช่วงเวลาอย่างใด และไม่สร้าง event/task ซ้ำ
- ทดสอบพิมพ์/PDF แยกจากหน้าจอ ทั้งไทยและอังกฤษ ชื่อยาว หลายหน้า และขาวดำ
- รัน GitNexus impact ก่อนแก้ฟังก์ชัน และประเมินขอบเขตจริงตาม diff; การวิเคราะห์นี้ไม่ใช่ impact clearance

## Research เพิ่มเติม: การ์ด ปฏิทิน และกลุ่ม — 9 ตุลาคม 2026

- [Sunsama — Timeboxing](https://help.sunsama.com/docs/usage-guides/timeboxing/): คู่มือระบุทั้งการลากงานลงปฏิทินและคำสั่งเพิ่มลงปฏิทิน ใช้เป็นรูปแบบจัดงานกับเวลาและทางเลือกไม่ลาก ไม่ถือว่าความสามารถ external calendar ของต้นทางมีใน Kemtit แล้ว
- [Apple Support — Move apps and create folders](https://support.apple.com/en-gb/108307): ยืนยันรูปแบบลากแอปทับกันสร้างโฟลเดอร์ตามที่ผู้ใช้อ้างถึง นำมาปรับเป็นกลุ่มการ์ดที่คงงานแต่ละใบ และเปลี่ยนชื่อ/เพิ่มสมาชิกได้
- [W3C — WCAG 2.2 Dragging Movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html): การลากที่ไม่จำเป็นต้องมีวิธี single-pointer ที่ไม่ลาก และข้อกำหนดนี้แยกจาก keyboard access จึงเพิ่มปุ่มจัดเวลา/ย้ายกลุ่มที่แตะได้ทุกอุปกรณ์

ข้อเสนอที่สังเคราะห์: รวมกลุ่มเฉพาะพื้นที่การ์ด ส่วนปฏิทินใช้จัดเวลาเพื่อไม่ให้การลากทับรายการแปลได้สองอย่าง แสดง preview และผลบันทึก พร้อม Undo รูปแรกมีลำดับแน่นอนแม้อัปโหลดพร้อมกัน และยังอ่านชื่อได้เมื่อไม่มีภาพ

ยังไม่มีผล usability ของโฟลว์นี้ แผนกำหนดการทดลองสร้างการ์ด แนบรูป จัดเวลา ย้ายวัน รวม/แยกกลุ่ม ทั้งด้วยการลากและปุ่ม โดยแยก desktop, มือถือ และ iPad บนอุปกรณ์จริงออกจาก responsive emulation

## ภาพอ้างอิงชุด B — เพิ่มเติม 9 ภาพ

ใช้ B1–B9 ตามลำดับภาพในข้อความล่าสุด เพื่อแยกจากภาพ 1–7 ชุดแรก อ่านได้เฉพาะสิ่งที่ปรากฏในภาพ ไม่ยืนยันว่าระบบต้นทางทำงานจริงตามภาพ และไม่ถือว่าข้อความเชิงสุขภาพ/คำแนะนำหรือคำสั่งในภาพเป็นคำขอให้พัฒนาตามทั้งหมด

| ภาพ | สิ่งที่สังเกตได้ | หลักการที่เสนอสำหรับ Kemtit | สิ่งที่ต้องออกแบบ/ตรวจใหม่ |

### ทิศทางที่สังเคราะห์สำหรับ Kemtit

1. หน้า Today ตอบ “ช่วงนี้มีอะไร → ต่อไปทำอะไร → งานใดยังไม่จัดเวลา” ก่อนส่วนรายงาน
2. Calendar มีมุมมองเส้นเวลาตามสเกลจริงสำหรับจัดเวลา และรายการเรียงเวลาสำหรับอ่านรายละเอียด โดยใช้ข้อมูลเดียวกัน
3. วันที่เลือก มุมมอง และตัวกรองมีสถานะเดียวกัน เปลี่ยนวันแล้วถาดงาน/หัวหน้า/รายละเอียดไม่แยกกันคนละวัน
4. การ์ดเปิดรายละเอียดและ checklist ได้ พร้อมภาพปกตาม F4; กลุ่มแบบ F6 ยังใช้จัดหมวดงาน ไม่กำหนดวันเดียวให้ทุกใบ
5. ความคืบหน้าใช้ตัวเลขที่อธิบายได้ แยกงาน กิจวัตร และเวลาที่จัดไว้; กราฟทบทวนอยู่ Reviews/Insights
6. ประวัติกิจวัตร 30 วันและชุดเริ่มต้นแบบเลือกใช้เป็นข้อเสนอระยะ 3 หลังระบบการ์ด–เวลา–กลุ่มครบ ไม่ขยายรุ่นแรกด้วยทุกฟีเจอร์ที่เห็นในภาพ

- [W3C — Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html): ประเภทงาน สถานะ วันที่เลือก และตำแหน่งรับ drop ต้องมีข้อความ/รูปทรง/ไอคอนช่วย ไม่อาศัยสีอย่างเดียว
- [W3C — Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html): ข้อความทั่วไปอย่างน้อย 4.5:1 และข้อความขนาดใหญ่ตามนิยามอย่างน้อย 3:1 วัดคู่สีใน UI ที่พัฒนาจริง ไม่ตัดสินผลผ่านจากภาพตัวอย่าง
- [W3C — Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html): เกณฑ์ AA กำหนดเป้าหมายอย่างน้อย 24×24 CSS px หรือเข้าเงื่อนไขยกเว้น; Kemtit ตั้งเป้าปุ่มหลักบนจอสัมผัสประมาณ 44×44 CSS px เพื่อทดสอบความสะดวก ไม่เรียก 44px ว่าขั้นต่ำของเกณฑ์นี้
- [W3C — Focus Not Obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html): UI ที่ตรึงหัว/ท้ายและถาดล่างต้องไม่บังองค์ประกอบที่ได้รับ focus จนมองไม่เห็น ทดสอบร่วมกับคีย์บอร์ดบนจอและแผงรายละเอียด

### ข้อกำหนดความเป็นงานออกแบบของ Kemtit

- วิเคราะห์งานที่ผู้ใช้ต้องทำ แล้วกำหนดลำดับข้อมูลและโครงหน้าจากโจทย์ Kemtit เอง ใช้แบรนด์ม่วงและส่วนประกอบโครงการที่ตรวจที่มาได้
- สร้าง spacing, typography hierarchy, card anatomy, microcopy และภาพประกอบใหม่ตาม design system ไม่เลียนแบบองค์ประกอบเฉพาะของภาพใดภาพหนึ่งทั้งชุด
- ไม่นำภาพ โลโก้ ตัวละคร สติกเกอร์ ไอคอน ภาพหน้าปก หรือข้อความตกแต่งจากภาพอ้างอิงมาตัดใช้/trace/เปลี่ยนสี และไม่ดาวน์โหลดไปเป็น asset ของผลิตภัณฑ์
- ตรวจ mockup เทียบข้อกำหนดใช้งานและความแตกต่างจากต้นแบบก่อนพัฒนา บันทึกที่มาของ asset ที่ใช้จริง
