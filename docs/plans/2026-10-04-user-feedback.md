## ขอบเขตที่ปรับแล้ว

Feedback เป็นฟอร์มสั้นสำหรับเก็บสัญญาณจากผู้ใช้: **เปิด → เลือกหนึ่งหัวข้อ → กดส่ง → แสดงขอบคุณ**

ไม่มีช่องข้อความ อีเมล ภาพแนบ หน้าประวัติ สถานะเรื่อง คำตอบจากทีม หรือขั้นตอนติดตามผู้ส่ง ไม่ต้องเชื่อม Feedback แต่ละรายการเข้ากับ Release notes

หน้า “มีอะไรใหม่” จากคำขอก่อนหน้ายังอยู่ในแผน เป็นข่าวสารแยกจากฟอร์ม Feedback

## 1. หน้าตาและการใช้งาน Feedback

ทางเข้าหลัก: “ส่งความคิดเห็น” ในเมนูโปรไฟล์ และลิงก์ในการตั้งค่า ใช้ ResponsiveDialog เดิม: กล่องบน desktop และแผงด้านล่างบน mobile

ตัวอย่างหัวข้อที่เสนอให้เลือกหนึ่งรายการ:

| รหัสที่เสนอ | ภาษาไทย | ภาษาอังกฤษ |
| --- | --- | --- |
| easy_to_use | ใช้งานง่าย | Easy to use |
| hard_to_use | ใช้งานยาก | Hard to use |
| slow | ระบบช้า | Slow performance |
| error | พบข้อผิดพลาด | Encountered an error |
| more_features | อยากได้ฟีเจอร์เพิ่ม | Want more features |

หัวข้อเหล่านี้เป็นชุดเริ่มต้นที่เสนอ ปรับข้อความได้ก่อนลงมือ ไม่มีหัวข้อ “อื่น ๆ” ที่เปิดช่องให้พิมพ์เพิ่ม และไม่เพิ่มคะแนนหรือคำถามหลายขั้นตอน

- แสดงหัวข้อเป็น radio options ที่กดได้ทั้งแถว พร้อมปุ่ม “ส่งความคิดเห็น”
- ต้องเลือกหัวข้อก่อนส่ง ไม่เลือกคำตอบไว้ล่วงหน้า
- หลังบันทึกสำเร็จแสดง “ขอบคุณสำหรับความคิดเห็น” และปุ่มปิด ไม่บังคับไปหน้าอื่น
- ขณะส่งปิดการกดซ้ำ หากส่งไม่สำเร็จรักษาหัวข้อที่เลือกไว้และให้ลองใหม่
- ไม่แสดงเลข ticket หรือส่งอีเมลตามหลัง

## 2. ข้อมูลที่เก็บและการนำไปใช้

ตารางใหม่ที่เสนอ `user_feedback`: id, user_id, request_id, topic_code, created_at

เก็บผู้ส่งจาก session เพื่อจำกัดความถี่และกันการส่งซ้ำ ไม่ขอข้อมูลเพิ่มจากผู้ใช้ ไม่เก็บข้อความ อีเมล สำเนาประวัติ หรือภาพหน้าจอ

เจ้าของโครงการดูจำนวนแยกตามหัวข้อและช่วงเวลาผ่าน Supabase ได้ในระยะแรก เช่น ผู้ใช้รายงานระบบช้าเพิ่มขึ้นหรือมีคนอยากได้ฟีเจอร์มากขึ้น ไม่จำเป็นต้องสร้างหน้าจัดการ ticket หรือสิทธิ์ทีม support

ข้อจำกัดของข้อมูล: หัวข้อ “พบข้อผิดพลาด” บอกแนวโน้มได้ แต่ไม่บอกขั้นตอนที่ทำให้เกิดปัญหา; หัวข้อ “อยากได้ฟีเจอร์เพิ่ม” ไม่บอกชื่อฟีเจอร์ การวิเคราะห์นี้ต้องตีความเป็นสัญญาณรวม ไม่ใช่ bug report ที่มีรายละเอียดครบ

### การบันทึก

- Server Action ตรวจตัวตนและ topic_code จาก allowlist ไม่รับ user_id จากฟอร์ม
- unique `(user_id, request_id)` ป้องกันรายการซ้ำ ใช้ request ID เดิมเมื่อลองส่งใหม่หลังเครือข่ายขาด
- request ID เดิมต้องผูกกับหัวข้อเดิม หากเปลี่ยนหัวข้อให้เป็นคำขอใหม่หลังทราบผลคำขอก่อนหน้า
- จำกัดความถี่ที่ฐานข้อมูลแบบ atomic ไม่ใช้การปิดปุ่มเป็นกลไกป้องกันหลัก ข้อเสนอเริ่มต้น 1 ครั้ง/นาทีและ 10 ครั้ง/วัน/บัญชี
- คำขอเดิมที่บันทึกแล้วคืนผลเดิมก่อนตรวจ quota ไม่ใช้ quota ซ้ำ
- RLS/grants/routine ป้องกันการปลอมผู้ส่ง อ่านรายการของคนอื่น และเขียนผ่าน API โดยข้ามข้อจำกัด
- anonymous และ session ที่ยังรอ OTP ไม่มีสิทธิ์ส่ง ระยะแรกใช้ auth/onboarding gate ปัจจุบัน
- กำหนดการเก็บและลบข้อมูลตามนโยบายโครงการก่อนเปิด hosted

## 3. Release notes — มีอะไรใหม่

คงหน้า `/updates` และ `/updates/[id]` สำหรับอ่านสิ่งที่เพิ่ม ปรับปรุง และแก้ไข เรียงตามเวลาเผยแพร่

- แต่ละรายการมีหัวข้อ รุ่น/build identity วันที่ และข้อความสั้นไทย/อังกฤษ
- เนื้อหาแบ่ง “เพิ่มใหม่ / ปรับปรุง / แก้ไข” พร้อมลิงก์ไปฟีเจอร์จริงเมื่อจำเป็น
- มี draft และ published; ผู้ใช้เห็นเฉพาะรายการที่เผยแพร่แล้ว
- ประกาศหลังตรวจรุ่นที่เปิดใช้งานจริง ไม่ถือว่า local QA หรือ merge เท่ากับ hosted release
- ใช้เครื่องหมาย “ใหม่” สำหรับรุ่นล่าสุด ไม่เปิด popup ทุกครั้งที่เข้าสู่ระบบ
- บันทึกการรับทราบต่อบัญชีและต่อรุ่นเพื่อใช้ข้ามอุปกรณ์ ไม่ถือว่าการเปิดเมนูคืออ่านแล้ว
- เจ้าของร่างและเผยแพร่ผ่าน Supabase ในระยะแรก ไม่มีหน้าผู้ดูแลเพิ่มเติม

ตารางใหม่ที่เสนอ: `release_notes` และ `release_note_reads` แยกจาก `user_feedback` ไม่สร้างความสัมพันธ์กับความคิดเห็นรายบุคคล

## 4. จุดเชื่อมและแผนพัฒนา

ข้อค้นพบจากการตรวจโค้ดเมื่อวางแผนก่อนหน้า: มี ResponsiveDialog และรูปแบบโมดูล core/ActionResult อยู่แล้ว; TopBar มี UserMenu สองชุดตาม breakpoint จึงต้องติดตั้งฟอร์มกลางเพียงครั้งเดียว ไม่ใส่ dialog ซ้ำในแต่ละเมนู

1. เพิ่ม migration แบบไม่ลบข้อมูลสำหรับ Feedback ตามหัวข้อ และข้อมูล Release notes/read state พร้อมสิทธิ์และ routine ที่จำเป็น
2. เพิ่ม schema/action Feedback, ฟอร์มกลาง และตัวเปิดจากเมนู/การตั้งค่า โดยรักษา query และฟอร์ม Quick Capture เดิม ไม่เปิดซ้อนกัน
3. เพิ่มหน้า “มีอะไรใหม่” คำแปลไทย/อังกฤษ และสถานะรับทราบ โดยไม่เพิ่มหน้าประวัติ Feedback
4. ตรวจฐานข้อมูลและ browser responsive แล้วจัดทำคู่มือเจ้าของสำหรับดูยอดตามหัวข้อและเผยแพร่ Release notes

ไฟล์ที่คาดว่าจะเกี่ยวข้อง: `UserMenu.tsx`, `src/app/(app)/layout.tsx`, หน้าการตั้งค่า, โมดูลใหม่ `src/core/feedback/` และ `src/core/releases/`, ฟอร์มกลาง, routes ข่าวสาร, types, messages, migration และ tests ไม่เปลี่ยน Login/OTP เพื่อทำงานนี้

ก่อนแก้โค้ดต้อง refresh GitNexus และทำ impact analysis ตาม AGENTS.md; เอกสารนี้ไม่แก้ฟังก์ชันแอป

## 5. เกณฑ์ตรวจรับ

- ผู้ใช้เลือกหนึ่งหัวข้อแล้วส่งได้จริงทั้งไทย/อังกฤษ desktop/tablet/mobile
- ไม่เลือกหัวข้อหรือส่งรหัสปลอมถูกปฏิเสธ ไม่มีช่องข้อความหรือขั้นตอนเสริม
- retry หลังผลลัพธ์สูญหายไม่สร้างรายการซ้ำ quota กันคำขอพร้อมกันได้
- auth/pending session และ direct Supabase API เคารพสิทธิ์ ไม่ปลอมผู้ส่งหรืออ่านข้ามบัญชีได้
- ปิด/เปิดฟอร์ม โฟกัส คีย์บอร์ด และ resize ไม่สร้าง dialog ซ้ำหรือทำ draft เพิ่มงานเดิมหาย
- Release notes ซ่อน draft ข่าวสารตรงกับรุ่นที่เปิดจริง และการรับทราบแยกตามบัญชี
- แยกผล local QA จากการเปิด hosted; ผลตรวจจริงและข้อจำกัดอยู่ในรายงาน QA ที่ลิงก์ด้านบน
