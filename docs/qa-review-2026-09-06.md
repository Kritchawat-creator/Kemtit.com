**ฉากที่ผู้ใช้ทำได้จริง:** สร้างเป้าปี Y → สร้างเป้าเดือน M (ก.ย.) ให้ Y เป็นแม่ → เปิด Y → แก้ไข → เปลี่ยนช่วงเป็น "สัปดาห์" เลือกวันในเดือน ก.ย. → dropdown "เป้าหมายแม่" เสนอ M ซึ่งเป็นลูกของ Y เอง → บันทึก

1. เรียก `candidatesFor` ตรง ๆ ตามฉากนี้ → ฟอร์มเสนอ "ลูกของตัวเอง" เป็นตัวเลือกแม่จริง

## A4. Service worker เก็บหน้าที่ล็อกอินแล้วไว้ 24 ชม. และ sign-out ไม่เคยล้าง — HIGH (privacy)

`src/app/sw.ts:22` (`runtimeCaching: defaultCache`) · `next.config.ts:8-13` · `src/core/auth/actions.ts:68-72`

ส่ง `defaultCache` ของ `@serwist/next` เข้าไปทั้งก้อน ซึ่งเป็น `NetworkFirst` + expiration 24 ชม. สำหรับ `others` (ทุก request same-origin ที่ไม่ขึ้นต้น `/api/`), `pages`, `pages-rsc`, `pages-rsc-prefetch` และ `apis` (GET `/api/*`) ส่วน `cross-origin` เป็น 1 ชม. · `NetworkFirst` ของ serwist ใส่ `cacheOkAndOpaquePlugin` เป็น default คือ **ตัดสินจาก status 200 อย่างเดียว ไม่ดู `Cache-Control`**

`signOut()` ล้างแค่ cookie — ทั้ง `src/` ไม่มี `caches.delete` หรือ `caches.keys` เลยแม้แต่จุดเดียว · precache manifest เองสะอาด (63 entry เป็น `/_next/static/**` กับ icon 4 ตัว) ปัญหาอยู่ที่ runtime cache ล้วน ๆ ซึ่งขัดกับ comment ที่เขียนไว้ใน `next.config.ts:8` ว่า "precache static shell, ไม่ cache การเขียน"

**ยืนยัน end-to-end บน production build จริง** (`pnpm build` + `pnpm start` พอร์ต 3100 เปิดด้วย Chrome จริง):

| สิ่งที่ตรวจ | ผล |
| --- | --- |
| service worker ติดตั้งและคุมหน้าเว็บ | `swActive: true`, `navigator.serviceWorker.controller` มีค่า |
| response header ที่ Next ส่งมาสำหรับหน้า HTML | `Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate` |
| หลัง reload มี runtime cache อะไรเกิดขึ้น | cache ชื่อ `others` มี `http://localhost:3100/login?next=%2Fdashboard` และ `/manifest.webmanifest` |
| เนื้อหาที่ถูกเก็บ | HTML เต็มหน้า 32,229 ตัวอักษร (มี markup ของแอปจริง) และ response ที่ cache ไว้ยังติด header `no-store` มาด้วย |

**ข้อแก้จากรอบแรก:** navigation ของหน้าเว็บตกลง cache ชื่อ **`others`** ไม่ใช่ `pages` เพราะ matcher ของ `pages` ดู `Content-Type` ของ **request** ซึ่ง navigation ไม่ได้ส่งมา — แต่ `others` ก็เป็น `NetworkFirst` 24 ชม. เหมือนกัน ผลลัพธ์จึงไม่ต่างกัน (RSC ของการกดลิงก์ในแอปจะตกที่ `pages-rsc` เพราะ request มี header `RSC: 1`)

**ฉาก:** ผู้ใช้ A ล็อกอินบนมือถือที่ใช้ร่วมกัน เปิด /dashboard และ /goals แล้วออกจากระบบ → ผู้ใช้ B เปิด PWA ตอนออฟไลน์หรือเน็ตล่ม → SW เสิร์ฟหน้าแดชบอร์ดของ A พร้อมเป้าหมาย งาน และชื่อที่แสดง

**แก้:** กรอง `defaultCache` ก่อนส่งเข้า Serwist — ตัด `others`, `pages*`, `apis`, `cross-origin` ออก (หรือเปลี่ยนเป็น `NetworkOnly`) เหลือเฉพาะ strategy ของ static asset · ถ้าต้องการให้อ่านออฟไลน์ได้จริงตาม Scope §9 ต้องออกแบบใหม่ให้ล้าง cache ตอน sign-out ด้วย

`src/core/goals/actions.ts:137-157` update แถวเดียว · archive เป้าเดือน "ยอดขาย กันยายน" แล้วเป้าสัปดาห์ลูกยังโผล่ใน `/goals` งานตัวอย่างยังอยู่บนแดชบอร์ด/ปฏิทิน และ back-link ของลูกยังชี้ไปแม่ที่ archive แล้ว · เอกสารไม่ได้ระบุ semantics — ต้องตัดสินว่า archive ควรลามหรือไม่ (ถ้าลาม ต้องจำว่าลามอะไรไปบ้างเพื่อให้ undo คืนได้ตรงชุด)

### C2. task รายสัปดาห์ไม่โผล่ในวัน `due_date` ของตัวเอง ถ้าวันนั้นไม่อยู่ใน BYDAY

`src/core/domain/recurrence.ts:34-39` ตีความ `due_date` เป็นแค่ขอบล่าง แต่ comment ใน migration (`20260905154811:86`) เขียนว่า "due_date เป็นวันแรกของ task ซ้ำ" ซึ่งคนละความหมาย · ฟอร์มก็ไม่ preselect วันของ `dueDate` → สร้างงานวันเสาร์แบบ "ทุกวันจันทร์" แล้วไม่เห็นอะไรเลยจนถึงวันจันทร์ · ต้องเลือกความหมายเดียวแล้วทำให้ตรงกันทั้ง 3 ที่

### C3. Batch 20 event ต่อรอบ อาจเกิน budget 10 วินาทีของ Netlify — [ประเมิน]

`processor.ts:11,97-116` ทำงานเรียงทีละ event · `line/client.ts:17-21` `fetch` ไม่มี timeout · ถ้า Supabase อยู่สิงคโปร์และ function รันที่ US ช่วง burst ตอนเช้าอาจถูก kill กลางคัน และ workflow (`--fail-with-body`) จะแดงทุก 5 นาที · ยังไม่ได้วัดจริง แต่ `AbortSignal.timeout` บน fetch ของ LINE ควรใส่ไว้ก่อน

### C4. ไม่มี lock/claim บน event ที่ดึงมา และ workflow ไม่มี `concurrency` — [ประเมิน]

`events/admin.ts:16-22` เป็น select ธรรมดา · `.github/workflows/cron-*.yml` ไม่มี `concurrency:` แต่เปิด `workflow_dispatch` → ถ้ารอบตามเวลากับรอบที่กดเองซ้อนกัน จะดึงแถวชุดเดียวกันแล้วส่งซ้ำ (คนละสาเหตุกับ known issue เดิมที่เป็นเรื่องลำดับ push → mark)

### C5. `config.toml` ชี้ seed ไปที่ไฟล์ที่ไม่เคยมี — [ยังไม่ยืนยัน]

`supabase/config.toml:70` ตั้ง `[db.seed].sql_paths = ["./seed.sql"]` แต่ `supabase/seed.sql` ไม่เคยมีใน repo · ยังไม่ได้ทดสอบว่า CLI จะ error หรือข้ามเงียบ ๆ ตอน `db reset`

# D. ช่องว่างของเทสต์

- ไม่มีเทสต์ route ของ webhook สำหรับเคสรหัสหมดอายุ, unique violation, และ source ที่ไม่ใช่ user
- ไม่มีเทสต์ `isAuthorizedCron` (secret ว่าง, scheme ผิด, `bearer` ตัวเล็ก) — e2e ครอบแค่ "ไม่มี header → 401"
- `scan-overdue.test.ts` มีแต่ happy path และเขียนเคส insert ล้มไม่ได้ เพราะ dependency กลืน error อยู่แล้ว (B1)
- `e2e/line.spec.ts:75-90` รวมยอด `sent` ของ user ทุกคนใน local DB แล้ว break ที่ตัวแรกที่ส่งได้ → regression ที่ `task.overdue` ไม่ส่ง อาจผ่านได้เพราะ `goal.completed` ของ spec อื่น
- `dayplan.test.ts` ครอบแค่ DAILY ที่ anchor อยู่ในอดีต จึงไม่จับ A6
- `onboarding.test.ts:30` ครอบ `//evil.example` แต่ไม่ครอบ backslash จึงไม่จับ A3
- ไม่มีเทสต์ cycle ของ `candidatesFor` / `buildGoalTree` (A1)

# E. ตรวจแล้วถูกต้อง (ไม่ใช่บั๊ก)

**เวลา/วันที่** — ทุกจุดที่หมายถึง "วันนี้" ใช้ `todayBkk()` และคำนวณบน ISO string ผ่าน `parseISO` local midnight ไม่เลื่อนวันบน server ที่เป็น UTC · `formatThaiDate` สร้าง Date ที่ UTC midnight แล้ว format ด้วย `timeZone: "UTC"` ปี พ.ศ. สม่ำเสมอทั้งแอป · สัปดาห์เริ่มวันอาทิตย์ตรงกันทั้ง `WEEK_STARTS_ON`, DayPicker, grid ปฏิทิน และปุ่มเลือกวันในฟอร์ม

**Security ที่ทำถูก** — webhook อ่าน raw body ก่อน parse, HMAC-SHA256 base64, `timingSafeEqual` พร้อมเช็คความยาว, ไม่มี header → 401 · cron auth prefix `Bearer ` ตรงตัว timing-safe token ว่างถูกปฏิเสธ handler เป็น POST ตรงกับ workflow รันบน Node runtime · link code 32^6 ≈ 1.07e9 modulo ไม่ bias TTL 10 นาที ล้างรหัสเมื่อผูกสำเร็จ มี unique index · service_role ทุก helper กรอง user id เอง

**RLS/grants** — ทั้ง 6 ตารางเปิด RLS และมี policy ครบทุก operation ที่ client ใช้จริง · `anon` ไม่มีสิทธิ์อะไรเลย · client แก้ `user_profiles` ได้เฉพาะ 5 คอลัมน์ที่ grant ไว้ (`display_name`, `active_persona`, `notify_overdue`, `onboarding_completed_at`, `avatar_path`) · `line_*`, `subscription_tier`, `last_overdue_notified_on` เป็นของ service_role · `handle_new_user` เป็น security definer ตัวเดียวและ pin `search_path`

**Schema** — คอลัมน์และ nullability ของ `src/types/database.ts` ตรงกับ DB จริงครบทั้ง 6 ตาราง · `goal_photos` และ `goals.cover_path` หายไปจากทั้ง DB และ types หลัง migration `20260906180000` แล้ว ไม่มีการอ้างถึงหลงเหลือ · Zod ↔ check constraint ตรงกันหมด (domain/persona/period enum, title 120/200, `target_value > 0`, `current_value >= 0`, regex ของ recurrence รับทุก string ที่ `formatRRule` สร้าง) · index ของ query หลักครบ

**Photos (ฝั่งที่ทำถูก)** — signed URL cache คีย์ `userId|hour|path` และ lookup ด้วย id ของเจ้าของเสมอ จึงข้ามคนไม่ได้ · `signedUrlWindow` ให้ URL เหลืออายุ ≥1 ชม. เสมอตอนข้ามชั่วโมง · ลงชื่อด้วย client ของ user ไม่เคยใช้ admin · policy ทั้ง 4 ตัวใช้ `(storage.foldername(name))[1] = auth.uid()::text` ถูกต้อง · path validation กัน `..` และบังคับ 3 segment · `file_size_limit` ของ bucket = `PHOTO_MAX_BYTES` · UI gating ครบทุกจุด และ photo count ไม่รั่วเมื่อ flag ปิด

**Progress/rollup** — ไม่ double count · metric ไม่นับ task ลูก · task ซ้ำไม่เข้า execution progress ตาม Decision · หาร 0 กันไว้ทุกทาง · clamp 0-100 · goal ของคนอื่นตกเป็น `notFound()` ไม่ใช่ throw

**i18n** — สแกนทั้ง repo: 410 message leaf / 377 call site → **missing key 0, namespace ผิด 0, key ที่ชี้ไป object 0, ICU error 0** · dynamic key ทั้ง 13 จุดขยายมือแล้วมีครบ · guard `t.has(key) ? … : t("generic")` ครอบทุก error key ที่ schema ยิงออกมาจริง

**อื่น ๆ** — bottom nav ไฮไลต์ถูกบน route ซ้อน (`/goals/[id]`) · FAB ซ่อนบนหน้าตั้งค่า · safe-area inset ครบทั้ง bottom nav, FAB และ bottom sheet ไม่มี `100vh` เหลือ · icon ของ manifest มีครบใน `public/icons/` และ `/manifest.webmanifest` กับ `/sw.js` ถูก whitelist ใน proxy · precache manifest ไม่มีหน้า authenticated · offline banner ไม่มี hydration mismatch · ติ๊ก/ยกเลิก task ซ้ำเขียน/ลบแถวของวันที่ดูอยู่ถูกต้อง กดรัวไม่ error เพราะ `ignoreDuplicates`

# หมายเหตุการทดสอบ

- ข้อมูลทดสอบทั้งหมด (เป้า cycle 2 แถว, task ซ้ำ 1 แถว) ถูกลบออกจาก local DB แล้ว · การทดสอบ `domain_events` ทำใน transaction ที่ `rollback`
- A1 reproduce ด้วยการเขียนแถวลง DB ตรง ๆ เพราะ Browser pane ถูกซ่อนอยู่ คลิกผ่าน UI ไม่ได้ (timeout) ส่วน "เข้าถึงได้จากฟอร์ม" พิสูจน์แยกด้วยการเรียก `candidatesFor` โดยตรง
- A4 ทดสอบ runtime จริงแล้วในรอบเสริม: `pnpm build` + `pnpm start` พอร์ต 3100 เปิดด้วย Chrome จริง (browser pane ที่ฝังในเครื่องมือติดตั้ง service worker ไม่ได้) · หลังทดสอบเสร็จ unregister service worker และลบ cache ทุกตัวออกจาก Chrome แล้ว และปิด server พอร์ต 3100 แล้ว
- การ build ทับ `.next` และ `public/sw.js` (ทั้งคู่อยู่ใน `.gitignore`) — ถ้าจะกลับไป dev ให้รัน `pnpm dev` ตามปกติ
- ตอนรัน E2E ฝั่ง desktop dev server log ขึ้น `Error: The destination stream closed early` 3 ครั้ง (ฝั่งมือถือไม่ขึ้นเลย) เทสต์ผ่านครบทั้ง 7 ตัว — น่าจะเป็น noise จาก Playwright ที่เปลี่ยนหน้าระหว่าง RSC stream ยังไม่จบ บันทึกไว้เป็นข้อสังเกต ไม่นับเป็นบั๊กเพราะยังไม่เห็นผลกระทบต่อผู้ใช้
- ยังไม่ได้ทดสอบ: offline จริงบนมือถือ, ติดตั้ง PWA บนเครื่องจริง, LINE OA จริง (ยัง dry-run)
